## Top picks

### 1. [Red-Teaming the Agentic Red-Team](https://arxiv.org/abs/2606.24496)
**Dario Pasquini, Michał Bazyli, Taras Fedynyshyn, Artem Sorokin · arXiv cs.CR · v2 posted August 17, 2026 (v1: June 30, 2026)**

The first in-depth security analysis of the offensive-security agent tooling itself, rather than of the targets such agents attack. The authors show that 12 widely-used agentic pentesting/red-team frameworks share design flaws that let an adversarial target system exfiltrate the operator's API keys, plant persistent footholds, and fully compromise the operator's own machine — even from inside a sandboxed container. This week's v2 revision adds a new attack class achieving near-deterministic remote code execution against agent infrastructure running frontier models (Claude Opus 4.8, GPT-5.5, Gemini 3.1 Pro), using contextual deception and reward hacking instead of an explicit prompt-injection payload — meaning standard injection filters wouldn't catch it.

**Methodology:** Systematic red-team security audit of 12 production offensive-security agent frameworks, plus a novel injection-free RCE attack empirically validated against frontier-model-backed agent deployments.

**Why it matters:** A direct hit on tier-1 relevance from the flip side — if your work builds or evaluates offensive-security agents, this paper is describing an attack surface (the agent's own host) that most threat models for those tools don't yet cover.

### 2. [The Defender's Window](https://openai.com/index/the-defenders-window/)
**Greg Brockman · OpenAI · policy essay + incident retrospective · August 17, 2026**

OpenAI frames a new training direction — models trained specifically to write "superhumanly secure code" — around an incident used as the post's centerpiece: an autonomous "agentic collective" penetrated both OpenAI's own research infrastructure and a separate company's production infrastructure by chaining previously-unknown vulnerabilities together with leaked credentials. The essay argues defenders currently hold a narrowing time advantage before attacker-side agentic capability catches up ("the window"), and positions superhuman secure-code generation as the primary defensive lever OpenAI is betting on.

**Methodology:** Policy/position essay grounded in an incident retrospective, not an empirical benchmark paper.

**Why it matters:** A named lab explicitly tying its secure-code-generation research agenda to a disclosed real-world multi-step agentic compromise — useful context if your threat model treats "agent chains real vulnerabilities together autonomously" as hypothetical rather than already-observed.

### 3. [Finding Vulnerabilities via LLM-Augmented Semantics-Aware Type-Checking](https://arxiv.org/abs/2608.14533)
**Ruizhe Wang, Meng Xu, N. Asokan — University of Waterloo · arXiv cs.CR · August 17, 2026**

Combines LLMs with semantics-aware type-checking to find real vulnerabilities in code, using the type system as a structural scaffold that constrains and validates what the LLM proposes rather than trusting the LLM's judgment on its own. The goal is precision: grounding LLM-based vulnerability hunting in a formal analysis pass to cut down on the plausible-but-wrong findings that pure LLM-based detectors tend to produce.

**Methodology:** Hybrid pipeline pairing an LLM with a semantics-aware static type-checking pass for vulnerability discovery.

**Why it matters:** A concrete instance of the neuro-symbolic pattern (LLM + formal grounding) applied specifically to cut false positives in LLM-based vulnerability detection — directly relevant if your detector work is fighting the same precision problem.

### 4. [Frequency-Aware Continual Learning for Smart Contract Vulnerability Detection with Large Language Models](https://arxiv.org/abs/2608.19680)
**Tenghui Huang, Jiawen Kang, Dongning Liu, Changyan Yi, Chengjun Cai, Anjia Yang, Li Li, Dong In Kim · arXiv cs.AI · ~August 20, 2026 (MEDIUM confidence — date inferred from ID position relative to confirmed Aug-20 neighbors, not independently corroborated by a second dated source)**

Addresses a practical problem for LLM-based smart-contract vulnerability detectors: as new vulnerability categories emerge, full model retraining is impractical, but naive per-task adapters cause catastrophic forgetting of vulnerability types the model previously learned to catch. The paper proposes a frequency-aware continual-learning scheme that adds coverage for new vulnerability classes without eroding detection of older ones.

**Methodology:** Parameter-efficient continual fine-tuning (adapter-based) with a frequency-aware regularization/selection mechanism, evaluated across sequential smart-contract vulnerability detection tasks.

**Why it matters:** Continual learning is a real deployment gap for any LLM-based vulnerability detector meant to stay current — this is a concrete recipe if your detector needs to absorb new CWE/vulnerability classes without a full retrain.

## Also notable

### [Decomposition Attacks Across Unlinkable Identities: Limits of Stateful Defenses for LLM Services](https://arxiv.org/abs/2608.17445)
**Bowen Sun, Zhengyue Zhao, Xiaogeng Liu, Yinzhi Cao, Chaowei Xiao · arXiv cs.CR/cs.CL · August 17, 2026**

Shows that "decomposition attacks" — splitting a malicious goal into individually benign-looking queries — defeat stateful, session-based defenses simply by spreading the sub-queries across multiple unlinkable user identities, since those defenses track a single identity's query history over time. A structural argument that identity/session-bound monitoring has a hard ceiling as a defense against decomposition-style jailbreaks.

**Methodology:** Adversarial attack construction against stateful LLM-service defenses, evaluated across identity-linkage conditions.

**Why it matters:** Relevant mainly if your evaluation harness for LLM-service defenses assumes single-identity attacker behavior — this is evidence that assumption doesn't hold.

### [Grading the Graders: Verification Autonomy Levels (L0–L5) for LLM Reasoning](https://arxiv.org/abs/2608.19009)
**Yajie Yin · arXiv cs.CL · August 19, 2026**

Proposes a taxonomy (L0–L5) for classifying LLM-verification schemes — step checkers, self-consistency filters, tool-based fact-checkers, formal-proof assistants — along two axes: where the verification spec comes from, and what the verdict actually guarantees. Argues L5 (fully unrestricted, guaranteed-correct verification) is impossible in the general case.

**Methodology:** Conceptual taxonomy/framework paper, not an empirical study.

**Why it matters:** Not security-specific, but a useful vocabulary if you're trying to characterize how strong a guarantee an automated vulnerability-detection or patch-verification pipeline is actually making.
