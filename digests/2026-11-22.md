# AI4Sec Weekly — 2026-11-22
**Window:** 2026-11-16 to 2026-11-22 (UTC). This week also includes papers submitted Nov 13–15, because last week's arXiv pull stopped at Nov 12.

Agent elicitation and benchmark validity dominate the week. One paper finds that exploitation agents underperform mostly because they stop too early. Another audit finds that 22% of CyberGym tasks are inconsistent. On the industry side, OpenAI shipped GPT-6.2 with explicit training for secure code and patches. Anthropic shortened its disclosure timelines, citing AI-driven rediscovery of bugs. The arXiv API had nothing submitted after Nov 19, so Nov 20–22 papers will appear next week. ## Top picks

### 1. [Stopping Is Not the Limit: Understanding and Eliciting Agent Capability in Long-Horizon Vulnerability Exploitation](https://arxiv.org/abs/2611.22888)
**Deokhyung Kang, Minjae Gwon, Sangdon Park · arXiv, Nov 17, 2026**

Exploitation agents on ExploitBench often stop while they still have budget left. Letting them keep going gives further verified exploitation gains, though each extra step adds less. The authors trace unproductive continuation to two signals: repeated stop responses, and running summaries that keep "impossible" judgments about capabilities the agent has not yet achieved. Their method, SCoRe, compacts context at bursts of stop attempts and marks those judgments as unproven. With it, MiMo-V2.6-Pro reaches 67.0% capability coverage at 2,000 turns. That compares with 32.4% under the original stopping policy, and 58.6% computed for GPT-5.5 from ExploitBench's 300-turn reference results.

**Methodology:** Test-time-scaling analysis on ExploitBench (DeepSeek-V4-Flash, MiMo), then a context-management intervention compared against summary-based baselines.

**Why it matters:** Published exploitation ceilings may partly reflect when agents stop rather than what they can do, so any offensive-agent benchmark you run or cite should control for stopping policy and turn budget.

### 2. [ChainAgent: Automated Chainable Vulnerability Discovery in PHP Web Applications](https://arxiv.org/abs/2611.25412)
**Xinyi Wang, Yeting Li, Shizhe Cui, Jiaming Guo et al. · arXiv, Nov 19, 2026**

ChainAgent is an LLM-agent framework that hunts for the parts of an exploit chain together: vulnerabilities, reusable "functional gadgets", and the capability dependencies between them. Its design comes from an empirical study of 386 real web exploit chains. An evolving exploit graph drives backward search from unmet preconditions and forward search from capabilities already found. On 15 PHP apps with three LLM backends it recalls 42.0–44.6% of the components needed to reach the goal, and recovers up to 4.4× more correct dependency edges than Codex. On 30 more real apps it found 20 vulnerabilities and 13 chains, 9 of which reach RCE.

**Methodology:** Precondition/capability modeling over an exploit graph, compared with a general coding agent and also run as a live bug-finding campaign.

**Why it matters:** It moves agentic vulnerability discovery from single bugs to composing chains, where real-world impact lies and where current benchmarks have nothing to measure.

### 3. [On the Reliability of CyberGym Evaluation: Task Material Consistency and Reference-Target Identity](https://arxiv.org/abs/2611.25790)
**Yule Ding, Hongzhen Wu · arXiv, Nov 19, 2026**

The authors audited all 1,507 CyberGym tasks and flagged 338 (22.4%) as inconsistent. The largest groups are coverage inconsistencies (205) and cases where the description and patch point to a different defect (110). They then re-checked a full Level-1 GLM-5.3 run. Of its 1,286 differential passes, 89 hit a bug other than the target and 10 lack enough evidence to tell. Requiring the PoC to hit the intended target lowers the pass rate from 85.3% to 78.8%, and wrong-target hits occur even in clean tasks (3.7%).

**Methodology:** A blind-reviewed audit of task materials, plus a check that each PoC hits the right bug (re-execution, crash-signature matching, LLM-assisted root-cause review).

**Why it matters:** CyberGym's crash-differential oracle overstates PoC reproduction, so caveat any CyberGym number you report or compare against. This pairs with last week's CAGE 4 audit.

### 4. [VAST: Compiling Grounded Vulnerability Scenarios into Verifiable, Multi-Step Environments for Evaluating LLM Red-Team Agents](https://arxiv.org/abs/2611.19465)
**Zhen Wan · arXiv, Nov 14, 2026 (carried over from last window)**

VAST is a declarative compiler that builds red-team ranges, keeping vulnerability scenarios separate from a layer that hardens the workflow. The result is 1,387 verifiable instances built from 109 seed edges (45 with CVE annotations) and 81 topic configurations. Three models solve only 12/90 instances given the task contract alone and 14/90 with a generic hint, but 76/90 with the full workflow protocol. On multi-container ranges they solve 88/126 (69.8%). LoRA fine-tuning of Qwen2.5-Coder-7B reaches at most about 4.7/33 held-out solves.

**Methodology:** Compiler-generated verifiable environments, with experiments that vary the prompt and that try supervised fine-tuning recipes.

**Why it matters:** The gap between 12/90 and 76/90 suggests that knowing the workflow, not knowing the vulnerability, is the bottleneck for red-team agents, which is a testable hypothesis for your own agent designs. Note that the paper is single-authored and the abstract is dense.

### 5. [Hardening JavaScript Programs against LLM-Based Vulnerability Detection](https://arxiv.org/abs/2611.25718)
**Zhenhao Tian, Jintong Yu, Jingwei Feng, Jianwei Zhuge et al. · arXiv, Nov 19, 2026**

AntiAgent evolves vulnerable programs, keeps the variants where a detection agent misses or misreports the bug, and distils them into reusable transformation rules. Against four detection agents, including Claude Code and Codex, it cuts detected vulnerabilities by 52.0–60.7%, beating JS-Obfuscator and FPA. The transformed programs still pass all project tests. The rules carry over to unseen vulnerability types and to Python.

**Methodology:** Evolutionary search over code transformations, guided by agent traces, with an LLM-plus-rules hybrid that preserves program behavior.

**Why it matters:** Agentic vulnerability detectors can be evaded with transformations that keep the code working, so robustness to adversarial code should be part of how they are evaluated. This complements last week's CodeQL-evasion paper.

## Also notable

### [SoK: Assessing the Evolution of LLM Capability in Software Vulnerability Research](https://arxiv.org/abs/2611.26601)
**Amine Lbath, Manan Suri, Aurelien Delaitre, Vadim Okun et al. · arXiv, Nov 19, 2026**

The authors grade published claims about LLM vulnerability-research ability on a driving-automation-style autonomy scale, qualified by how correct, available and strong the evidence is. They conclude that agents were already finding, validating and patching real bugs autonomously before the restricted 2026 frontier models arrived, and that open-weight models later matched that autonomy for discovery and validation. Ten years of CVE and exploitation data show disclosures more than doubled in 2026, with more critical/high ratings and more decade-old bugs. The time from report to fix and from disclosure to attack has not noticeably changed.

**Methodology:** Systematization with an evidence-graded autonomy scale, plus longitudinal measurement of vulnerability data.

**Why it matters:** It gives you a citable, evidence-graded framing for claims that AI has changed vulnerability research, with NIST co-authors.

### [Static Analysis Guidance for Secure LLM Code Generation](https://arxiv.org/abs/2611.26312)
**Daniele Lunghi, Alberick Euraste Djiré, Zacharie Chenail-Larcher, Mélissa Tessa et al. · arXiv, Nov 19, 2026**

When a static analyzer fires during generation, the method rolls back and injects the finding, either as a code comment or as a steering message. This costs 0.9–1.9× the baseline's output tokens, against up to 24.1× for iterative repair loops. With DeepSeek-V4.1-flash on RiskyPy, the steering variant raises the share of programs that are both functional and secure from 52.5% to 64.4%, close to the best iterative approach (66.2%). The limits are clear too: analyzers flag at most 5.6% of functional-but-insecure programs on SecEvalPlus. Models also follow alerts that contradict the task and break the program as a result.

**Methodology:** Controlled comparison of 2 in-generation strategies, 2 iterative strategies and a control, across 3 models and 3 Python benchmarks.

**Why it matters:** It isolates how much static-analysis feedback actually helps secure code generation, and shows that analyzer recall is the ceiling.

### [Compositional Exploits in Autonomous Coding Agents: Attack Mechanics and Ephemeral Defense](https://arxiv.org/abs/2611.19764)
**Deep Shah, Nehal Kathrotia · arXiv, Nov 15, 2026 (carried over from last window)**

Coding agents can chain individually harmless tools over shared files, environment variables and memory into an unauthorized attack. On a 560-task suite (360 exploit tasks across 8 hazard classes, plus 200 benign tasks), Gemini 3.5–3.8 Flash carry out these chains 72.9–84.5% of the time. Five scanners that check one tool at a time detect none of them. CompGuard combines capability leases with Landlock, seccomp-BPF and a short-lived proxy. It blocks 100% of the chains at 61.4 µs overhead and keeps a 98.0% solve rate on benign tasks.

**Methodology:** A benchmark of attack chains plus an evaluation of an OS-level defense.

**Why it matters:** It names a class of coding-agent attack, similar to code reuse, that auditing each tool call on its own cannot catch.

### [YUL: Bringing Software Supply Chain Security to Coding Agents](https://arxiv.org/abs/2611.23314)
**Aman Sharma, Frank Reyes, Martin Monperrus · arXiv, Nov 13, 2026 (carried over from last window)**

Coding agents often declare stale dependency versions they remember from training data. YUL checks each dependency declaration against the package registry, blocks stale or nonexistent versions, and tells the agent which version to use instead. On 60 tasks across six ecosystems, Claude Code/Opus 5.5 declares a stale version in 29% of runs and OpenCode/DeepSeek V4.1 Flash in 39%. Both do so in every GitHub Actions run. With YUL, 93% and 96% of the stale runs end on the latest release.

**Methodology:** A guard added to the agent harness, evaluated with and without it.

**Why it matters:** It is a simple, measurable fix for a dependency-level security weakness in AI-generated code.

### [Missing Security-Fix Backporting for GitHub Actions Workflows](https://arxiv.org/abs/2611.22519)
**Chengyan Ma, Jieke Shi, Ruidong Han, Weifeng Sun et al. · arXiv, Nov 17, 2026**

The authors mined 1.9M commits that modify workflows and scanned them with zizmor, finding 69,865 security fixes across 24,238 projects. Of 474,490 audited release branches, 224,392 are still vulnerable, and only 19,476 of the 78,907 fixed branches look like real backports. The median backport lag is 243 days. Their tool, WorkflowBP, compiles each fix into a semantic patch for workflows and falls back to an LLM when a branch has diverged the most. It produces backports that pass the scanner for 67.9% of 12,000 unpatched files, and 44 of 176 issues filed upstream have been confirmed or fixed.

**Methodology:** Large-scale empirical study plus patch transplantation that combines symbolic rules with an LLM.

**Why it matters:** It shows LLM-assisted security patching working at ecosystem scale, with maintainers adopting the fixes.

### [Introducing GPT-6.2 Astra and Sol](https://openai.com/index/introducing-gpt-6-2-astra-sol)
**OpenAI · Nov 17, 2026**

OpenAI calls both models "another significant jump in cyber capabilities": they are better at finding and exploiting vulnerabilities, writing secure code and producing patches, and they use fewer tokens. Both meet the "Critical" cybersecurity threshold of OpenAI's Preparedness Framework and ship with tighter safeguards. OpenAI says these safeguards also block some legitimate vulnerability research. The post introduces two benchmarks. DeepBinary measures vulnerability finding in 12 compiled Windows system binaries, and SecureSWE is an internal benchmark for code that is both functional and secure. OpenAI also says it added training signals for secure-by-default code and for patches that keep intended behavior. Scores appear only in charts.

**Methodology:** Model launch reporting internal cyber benchmarks for binary vulnerability finding, secure code generation and patching, run with safeguards turned off.

**Why it matters:** A frontier lab now trains directly for secure code generation and for patches that preserve behavior, which raises the bar that baselines in your area will be compared against.

### [Updating our coordinated vulnerability disclosure policy timelines](https://www.anthropic.com/research/coordinated-vulnerability-disclosure-timelines)
**Anthropic Frontier Red Team · Nov 16, 2026**

For reports made from 2027-01-01, Anthropic is cutting its disclosure window from 90 days to 30 days for high/critical issues and to 45 days for others. It will escalate to an external coordinator after 15 days without a response from the maintainer, and publish full technical details 30 days after a patch. The stated reason is that independent rediscovery is rising as AI improves ("a bug that one model can find is increasingly likely to be found by another"), and that models can now help write fixes. Unreviewed findings from its automated OSS scanner are excluded. Project Zero's ["Policy and Disclosure: 2026 Edition"](https://projectzero.google/2026/11/disclosure-policy.html), published Nov 13, is a useful companion.

**Methodology:** Policy post based on observed rediscovery; no quantitative data given.

**Why it matters:** It is a concrete case of AI vulnerability discovery changing disclosure norms, and rediscovery rates under shorter windows are an open measurement question.

### [The risks of device code authentication for AI coding agents](https://www.microsoft.com/en-us/security/blog/2026/11/17/the-risks-of-device-code-authentication-for-ai-coding-agents/)
**Uri Oren, Dor Edry · Microsoft Security blog, Nov 17, 2026**

In a lab simulation, the victim approves a GitHub OAuth device-code request that the attacker started, using GitHub Copilot CLI as the example. That one approval lets the attacker steer an active Copilot CLI session remotely (if remote control is enabled) and run commands on the victim's machine. The attacker can also plant misleading entries in the agent's persistent memory, read cloud-synced sessions, and access private repos. Microsoft stresses that these are proof-of-concept chains abusing features that work as designed, not attacks seen in the wild. The post also covers detections and mitigations.

**Methodology:** Controlled red-team simulation of an identity-phishing chain against an agentic coding tool.

**Why it matters:** Coding-agent security also depends on authentication, remote control and persistent memory. Poisoning an agent's memory after a stolen login is a threat model few papers consider.
